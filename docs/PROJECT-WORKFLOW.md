# 项目执行与断点规范

本项目每个发布周期只有一个经过用户明确授权的产品版本。当前周期的机器可读政策位于 `config/release-policy.json`；VERSION、应用元数据、工作流、归档名、tag 和 Release 必须与它一致。构建尝试使用 `build-NNN`，不得通过递增产品版本记录进度。

## 范围与推进顺序

修复对象是本仓库 ai-support 及其已承诺的客服和管理功能。第三方项目只能用于核对具体契约或实现，不自动成为待开发组件；外部历史消息或他人服务的问题，也不能未经归属核实就升级为本项目缺陷或新增发布门槛。已有有效保护须保留，确实阻止合法流程的保护按本项目需求修正，不为得到通过结果而清除人工、去重、回执或未完成任务。

当前任务单记录本轮目标、非目标、已授权环境、必须保留项和验收结果。工程判断遵循用户指定的 [Stop That Shit](https://github.com/lennney/stop-that-shit/blob/main/skills/stop-that-shit/SKILL.md)，不额外安装 Guard 或引入另一套流程。普通技术细节直接处理；仅在缺失信息会实质改变范围、权限或不可逆选择时请求决定。历史审计编号用于定位，不是自动修复清单。Haruka-Network/CrispAI 不是用户项目，不作为修复对象；Wallos 等成熟实现只用于有日志依据的参数、协议或响应差异对照。

| 阶段 | 本阶段交付与进入下一阶段的条件 |
| --- | --- |
| 只读复核 | 当前故障、责任模块、实际日志、既有修复与证据缺口；不夹带安装、业务修改或测试。 |
| 流程与任务确认 | 沿用本文件、测试说明及现有任务单；明确一个可验收结果、影响范围、预算和停止条件。 |
| 定向实现 | 先确认可达根因，再作最小必要修改；不引入无关重构、另一套框架或额外外部兼容。 |
| 受影响验证 | 选择现有最小适用检查；配置及代码在授权环境实际加载后，检查业务结果与对应日志，并保留正常反例。 |
| 功能收口 | 核对当前承诺功能的剩余缺口，复用有效结果；未执行但必要、确实不适用、失败必须分别记录。 |
| 指定候选发布 | 候选不再有范围内阻塞后冻结，执行既定同包门槛及交付；不临时扩写认证范围。 |

修复顺序以实际故障和用户最新指令为准。组件启动、模型调用、业务答案、发送确认与辅助收尾分别判断；不能用命令结束、日志中的成功、健康状态或发出固定文字代替问题解决。必要结果满足后结束该任务，不追加没有新问题或证据失效依据的验证。

## 断点记录

开发过程在被 Git 忽略的 `.work/<版本>/control/` 维护唯一状态：

- `CURRENT.md`：当前提交、构建、步骤、活跃操作、下一动作和阻碍；
- `TASKS.md`：步骤状态；
- `DECISIONS.md`：技术选择及理由；
- `OWNERS.md`：共享文件与远程操作所有权；
- `TEST-LEDGER.md`：场景、源码/依赖/配置绑定、结果和失效原因；
- `EVIDENCE-INDEX.md`：证据位置索引；
- `RELEASE-STATE.json`：版本、冻结、目标机验收和发布开关。

恢复会话或更换执行者时，先依次读取 `AGENTS.md`、CURRENT、TASKS、当前步骤和测试账本，再核对源码与仍在运行的进程。上下文压缩、输出截断或换执行者本身不构成重跑依据。

## 证据复用

每条证据绑定场景、测试代码、被测生产依赖、固定组件、配置代次、执行位置和结果。相关生产模块、生成工作流、关键数据结构或配置改变时，仅使受影响场景失效；纯文档修改不要求重跑模型和索引测试，但最终归档身份仍需重新核对。

同一代码、输入和环境连续两次出现相同失败后，下一次执行前必须新增根因假设、观测点或最小复现。长任务中断后先核对 PID、启动身份、锁和已有结果，不能未经确认并行启动第二份。

## 测试与资源停止规则

测试选择入口为 [测试与验收](TESTING.md)。主驱动与单项检查是不同入口，不把两者连续全部运行作为每次修改的默认流程。已有覆盖不足时补必要场景；共享边界改变时扩大到实际下游，不以文件数量代替影响分析。

每次开始前在现有任务单列出：要证明的结果、真实命令、相关代码/配置、授权环境和副作用、累计测试预算、单命令时限、修正轮数及重跑理由。无可靠费用或 Token 数据时写不可观测，不以耗时猜费用；预算未明确时不自动沿用一次长任务的最大时限作为新任务预算。

默认不新增子 Agent，不安装插件、Guard 或 Skill；需要时单独明确授权。时限由既有执行器落实，不能把测试名称、运行编号、重启或轻微参数变化当作预算重置。

同根因连续两次相同失败，先复盘实际日志和假设，再决定下一步；累计十次仍无有效结果时停止原试错方式，查阅相关成熟实现并说明新的因果依据。达到预算或修正上限就报告未完成与必要决策，不能改断言、取消有效保护或继续无依据重复。

长任务只续同一次仍活跃的执行，读取摘要和必要失败片段；确认终态后才安排后续。只更新现有账本和必要交接，不为每个检查新增独立报告、证明层或同义测试平台。账本顶部和 RELEASE-STATE 只指向一个当前动作、候选与活跃句柄；已结束的执行明确作为历史，不让旧 RUNNING/BLOCKED 覆盖新事实。流程文档只作必要调整后一次冻结，不因每条观测重写报告、重新打包或重做业务验收。正式发布既定要求的独立回执不因此取消。

## 发布边界

核心目标是持续维护 ai-support，不绑定历史发布版本；每轮交付使用用户明确指定、与当前发布政策一致的版本。产品开发、构建及业务测试仍在 TARGET-A；源码、测试与文档先在 TARGET-A 修改并检查实际结果，再同步仓库。用户第十二份明确允许仅空机安装在 Codex 本机隔离 Debian12 虚拟机执行，发布后匿名公开命令实装沿用这一例外；其它开发机职责仍为阅读、同步、Git 身份核对、GitHub 认证和最终发布。虚拟机不得接入 TARGET-A 真实配置、客户资料或凭据，须实际由生产安装器补齐缺失依赖并运行本项目；结束保留必要脱敏结果后销毁本次自有 VM、基础镜像和测试磁盘。旧环境失败和累计次数保留，硬件或授权确实变化才记录新执行依据，不以重命名重置预算。TARGET-A 同包业务验收与该空机门槛均完成前，不得 push、创建 tag、draft 或 Release。正式包 SHA、公开 Release 与匿名回下载结果写入包外独立核验回执，不修改已验收归档造成重复冻结。
