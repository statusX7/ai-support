## 3. 确认缺陷、根因与修复

### V122-01：全新安装在十项确认后被 Compose 候选校验中断

- 位置：`install.sh` 的首次配置提交与 `configure_webhook_access` 调用；严格回归在 `tests/test_install_resume.sh`、`tests/mocks/docker`。
- 复现：从公开 v1.2.1 在无 Docker/Compose 的干净 Debian 12 amd64 VM 原样执行新手命令，完成 10/10。依赖与 Docker 已自动安装，但第一次 Webhook/Caddy 候选校验调用完整 `docker compose config`；此时已经验证的 AI 模型、AnythingLLM Key、Crisp 鉴权等后置字段尚未写入 `.env`，Compose 按设计拒绝缺失变量。
- 根因：单个候选的预检错误依赖尚未提交的整份持久配置；问题不是 Docker 未启动、Key 无效或用户漏填。
- 修复：保留既有“Webhook/Caddy 候选成功后才允许 Provider 提交”的恢复顺序，只把内存中已经通过 schema/边界校验的候选字段传给本次 Compose 子进程。预检成功后才原子写入持久投影，不新增第二份权威配置源，也不放宽 Compose 必填项。
- 回归：全新严格 Compose 路径必须到达可续装状态；受管 Caddy 候选故障发生在 Provider 探针/提交之前，接口池、秘密代次、旧 `N8N_HOST` 和 Caddy 有效代保持。

### V122-02：`staged` 部署无法作为完整配置继续启动

- 位置：`install.sh` 的部署状态分流与保留配置校验。
- 复现：新安装显式 `--skip-start` 后再次正常执行，旧逻辑没有把 `staged` 视为可复用配置，会返回初始化路径。
- 根因：状态机只覆盖 `installing`/安全卸载保留资料，没有为“文件与配置已完整、服务尚未启动”建立恢复分支。
- 修复：`staged` 必须通过完整 `.env`、业务配置、接口池与秘密引用校验后才能复用；随后不重输十项、不重生成内部 Key，并继续真实服务启动与验收。不完整的 staged 仍回到必要初始化。
- 安全边界：已有实例不得把 `--reconfigure` 与 `--skip-start` 合用；该组合在任何配置、Provider 探针或 Docker/Caddy 变更前以中文拒绝。

### V122-03：人工期旧消息在恢复后迟到会被当作新问题补答

- 位置：`n8n/runtime.js` 的 `message:send` 持久接收；回归在 `tests/test_runtime_missing_reply_p0.js`。
- 复现：真人暂停期间访客已发送消息，但 Crisp 在会话自动恢复后才重投该事件。旧逻辑只看收到时会话已是 AI，因而把人工期问题加入新代次。
- 根因：恢复已有 `control_watermark`，接收分支却未比较事件时间与控制水位。
- 修复：事件时间早于水位的旧消息保留去重事实并直接终态，不补答；恰好位于恢复边界及之后的新消息仍正常入队。该规则不改变真人的即时暂停和 3600 秒默认恢复。

### V122-04：Provider 配置事务会阻塞不依赖模型的本地动作

- 位置：`n8n/runtime.js` 的 receive/makePlan/knowledgePlan；回归在 `tests/test_feedback_runtime.js`。
- 复现：接口池处于受管应用窗口时，新鲜固定回复、人工关键词确认和本地菜单与普通模型问答一起被提前 defer。
- 根因：是否需要 Provider 在计划生成前还未知，旧入口把所有非控制消息一刀切标为接口依赖。
- 修复：在有效业务投影上先规划本地规则/菜单/人工 offer；进入 Crisp 历史、知识检索或模型调用之前再执行 Provider 代次栅栏。真正的 AI/图片/Prompt 任务保留原始数据并持久延后，事务完成后按新 revision 恢复一次；等待期间不发生历史读取、检索或模型调用。

### V122-05：慢推理可占满 n8n Code runner，使新 Hook 在持久化前排队

- 位置：生成工作流的 Hook→receive→respond→process 顺序、`n8n/runtime.js` 的普通任务执行，以及 Compose 的 runner 并发契约。
- 复现：锁定 n8n 镜像默认 Code runner 最大并发为 10。隔离工作流中 9 个慢处理时新 Hook 约 0.03 秒返回；10 个慢处理时 healthz 仍正常，但下一 Hook 的 receive Code 直到首个慢任务释放才运行，约等待 11.8 秒。
- 根因：Respond Webhook 后同一 execution 继续等待长 `runtime.process`；调度扫描还能一次启动多条普通任务，现有单会话 worker 锁不能保护全局 Code runner 容量。
- 修复：n8n runner 固定为 10；后台处理共用 8 个跨 execution 的有界租约许可，普通长任务最多占 7 个，始终给 Webhook 等轻量入口保留 2 个 runner。控制任务优先使用专用第 8 个后台槽，控制积压与普通任务并存时扫描仍给普通任务保留一个名额。拿不到许可立即原子退回持久队列并短延后，不在 Code node 内等锁；崩溃、重启和过期许可按严格文件类型、kind、槽位、所有权 token、心跳与快照身份回收。
- 修后证据：固定 `docker.n8n.io/n8nio/n8n:2.33.0` 中，7 个普通慢任务并发峰值为 7，新 Hook 为 HTTP 200、约 0.183 秒；8 个慢控制任务并发峰值为 8，第 9 个控制 Hook 约 0.099 秒、新访客 Hook 约 0.128 秒完成持久接收，两个溢出任务均保持 `received`、未领取 worker/lease 且未增加尝试次数。该证据是 REAL-LOCAL 生产工作流压力验证，不是 Crisp 公网投递时延。

### V122-06：后台许可换代后，旧执行仍可能写状态或出站

- 位置：`n8n/runtime.js` 的跨 execution 后台许可、网络调用及 `process` 收尾；回归在 `tests/test_runtime_missing_reply_p0.js`。
- 复现：执行许可过期或被新 owner 安全接管时，旧 Code execution 已持有任务快照和网络操作；只限制新任务取得许可，不能阻止旧所有者继续完成写入。
- 根因：容量限制和执行权是两个不同问题，旧实现没有把许可所有权 token、进程/启动身份、心跳及取消信号贯穿每个耗时边界。
- 修复：每个处理 claim 绑定不可变许可和 AbortSignal；历史读取、检索、Provider、Crisp 查询/发送及事务写回均复核所有权。丢失所有权立即取消，任务以短延后回到持久队列，本地换代不增加业务 attempts；已经取得确定 Crisp 回执的任务只记账，不重新发送。

### V122-07：上游或旧待发计划仍可能把机械故障话术交给访客

- 位置：新增 `scripts/visitor-output.js`，由 `scripts/provider-adapter.js`、`n8n/runtime.js` 和生成工作流共同消费；回归在 `tests/test_provider_adapter.js`、`tests/test_runtime_provider_pool.js`、`tests/test_runtime_provider_failure_reply.js`。
- 复现：上游可返回 HTTP 200 但正文只有系统忙、稍后重试等机械话术；全池 401/429/超时/错误 JSON、adapter 中断及升级遗留计划也可能走不同兜底出口。
- 根因：各出口分别判断响应有效性，缺少“尚未确定送达前”的最终访客可见内容收敛层。
- 修复：纯机械故障答复继续按 `invalid_response` 有界切换；全部候选用尽或本地恢复失败时统一生成一次具体自然澄清。正常业务状态、带实际排障步骤的正文、安全拒答、Prompt、知识和已经发送/回执未知的历史正文不被改写。
- 回归：真实 adapter 子进程串接受控 401、429、网络超时、HTTP 200 错误 JSON及进程中断，5/5 均只出站一条自然澄清；重复 Hook 不再次调用 Provider 或发送。

### V122-08：恢复水位后的无时间事件无法安全判断是否属于人工期

- 位置：`n8n/runtime.js` 的 `receive`、`resolveVisitorEventTime` 和 `process`；回归在 `tests/test_runtime_missing_reply_p0.js`。
- 复现：恢复后收到缺失或损坏 timestamp 的访客 Hook，若直接用本机收件时间会把人工期旧问题误当作新问题；若一律丢弃又会吞掉真实新消息。
- 修复：先持久接收但不读历史、检索或推理，再按当前站点/会话/fingerprint 访问 Crisp 精确消息端点确认官方时间。确认新消息才继续，确认早于水位则终态去重；权限或网络长期无法确认时有界收敛为不补答，不猜时间。

### V122-09：Website Hook 未到达时，本机没有可恢复任务

- 位置：`n8n/runtime.js` 的 `performCrispRestCatchup`/`catchup`、`n8n/build-workflow.js` 的五秒调度，以及 `scripts/doctor.sh`；回归在 `tests/test_runtime_missing_reply_p0.js`、`tests/workflow-runtime.test.js`、`tests/test_doctor.sh`。
- 复现：Crisp 历史中存在访客消息，但对应本机没有 receive/job/attempt/outgoing 事实。既有持久队列只能恢复已经到达的 Hook，不能创造从未收到的入站记录。
- 根因：Website Hook 实时入口没有同等失败重试保证，运行时也没有当前站点的补偿水位。
- 修复：首次启用只从当前建立绑定水位，避免回复历史会话；之后按五分钟窗口、有限页和每轮最多三个会话消息请求，从官方 REST 找回访客及真人公开消息，并调用同一 `receive` 链。水位/页/消息游标持久化，重复与重启幂等；独立锁且与本地 `scan/process` 并行，REST 超时不会拖住已有任务。doctor 只展示脱敏状态、水位延迟及错误分类。

### V122-10：恢复安装只设置兼容模型字段时，候选预检使用了空模型

- 位置：`install.sh` 的候选环境归一化；回归在 `tests/test_install_resume.sh`。
- 复现：旧配置仅含 `DEFAULT_AI_MODEL` 而没有新投影字段时，恢复路径能读取模型，却在 Webhook/Caddy Compose 预检与接口池提交的一个分支传入空值。
- 根因：同一候选在两个生命周期阶段使用了不同的环境变量回退表达式。
- 修复：一次生成 `AI_MODEL_CANDIDATE_VALUE`，由候选 Compose 和最终接口池提交共同使用；合法旧值不被示例覆盖。

### V122-11：发布包可能与已验收工作树或 TARGET-A 候选不同

- 位置：`scripts/release-manifest.txt`、`scripts/package-release.sh`、`scripts/release-gate.py`、`scripts/publish-release.sh` 及 `tests/test_release_identity.py`。
- 风险复现：从活动目录打包会混入未跟踪模块或漏掉新增运行文件；目标机验收另一个候选后再改包，仍可能沿用旧回执发布。
- 修复：只接受干净提交，从固定清单读取 HEAD blob 构建规范化归档；门禁逐成员校验内容、模式、顺序、版本和 workflow。TARGET-A 回执必须绑定同一 commit 和归档 SHA，并在任何 push、tag 或 draft 之前验证。远端 tag/Release 仍不可覆盖。

### V122-12：TARGET-A 指定旧会话的“未回复”实际属于人工暂停，另有 Hook 漏投样本

- 现场仅记录脱敏事实：用户指定会话中的访客消息之前约五秒已有非本项目 `operator:text` 公开回复。该事件被持久识别为真人并立即暂停本会话，因此该访客任务为 cancelled、Provider 尝试和自动出站均为 0；这符合人工优先规则，不是推理故障。“已就绪”也由 Crisp 记录为 operator 公开回复，正确刷新了该会话人工期限。
- 独立核对近一日记录时，另发现 Crisp 历史中有两条访客消息没有本机 durable job；现有证据只能定位在 Hook 未到达/接收前过滤/持久窗口，不能凭事后数据库把三者进一步伪分。V122-09 为这一类“本机从未形成任务”的缺口增加补偿。
- 当前版本实机对照：新建隔离 Web SDK 访客只发送一次，五秒内完成官方访客消息、生产 Hook、durable job、一次 Provider 成功、本项目 `outgoing=sent` 和同 fingerprint 回到 SDK；恰好一条回复、无评价邀请、会话仍为 AI、总开关未变。候选正式部署后的补偿、知识、人工和重启门槛仍在冻结阶段复验，不能用这次基线对照代替最终同包验收。

### V122-13：doctor 把 n8n 已软删除的完成记录误报为活动执行积压

- 位置：`scripts/doctor.sh` 的 `doctor_n8n_execution_backlog_check`；回归在 `tests/test_doctor.sh` 及其 Docker fixture。
- 现场复现：直接按 `status IN (new,running,waiting)` 查询会得到持续增长的记录，看似 Code runner 长期占满；进一步只读核对发现这些记录全部已有 `deletedAt`，而未软删除的活动记录为 0。调度心跳持续完成，新建真实 SDK 会话也在五秒内完成单次回复。
- 根因：固定 n8n 2.33.0 在成功/错误执行均配置为不保存且启用 pruning 时，完成钩子会把 in-flight execution 标记软删除，保留原 status 直到后续硬清理。旧 doctor 没有按 n8n 当前活动记录过滤墓碑。
- 修复：积压 SQL 同时要求 `"deletedAt" IS NULL`；诊断不清数据库、不重启服务，也不把软删除记录当 runner。fixture 分别覆盖软删除 running 不计入、未删除 running 才计入。

## 5. 验证方法与发布事实边界

本版新增测试入口为 `tests/test_install_resume.sh`、`tests/test_runtime_missing_reply_p0.js`、`tests/test_feedback_runtime.js` 及固定 n8n runner 饱和夹具。当前聚焦结果：workflow runtime 45/45、评价/业务 runtime 57/57、漏回复 P0 14/14、Provider pool 33/33、安装恢复 4/4；固定镜像压力结果见 V122-05。最终主驱动、真实 Compose/n8n/AnythingLLM、v1.2.1 升级与失败回滚、TARGET-A 同一冻结包、公开匿名下载和干净 VM 原样命令仍按发生顺序记录，未发生的发布事实不预填。

测试分层、最终通过/失败/跳过数、候选包 SHA、TARGET-A 非敏感故事和正式 Release 状态在冻结后填写到独立核验回执。协议 fixture 不写成真实供应商，宿主 healthz 不写成客服往返；一轮失败后重跑不累计制造通过数。

## 6. 已知边界

- 跨 Provider、Crisp、公网与访客终端无法保证数学意义上的“任何时候绝对送达”。本项目保证本机可持久接收时不静默丢任务、上游可用时有界故障切换、发送前复核人工/总开关，并对不确定回执有限对账；明确拒绝、所有接口不可用、网络分区或平台长期不可查时会留下可诊断失败。
- v1.2.2 不替用户创建备用账号或额度。最多 20 个备用是软件容量，不代表每次调用 21 个接口，也不代表已真实配置 21 家供应商。
- 已经被 Crisp 接收的在途 HTTP 消息无法事后撤回；真人事件在本机确认后会中止尚未发送或仍可取消的结果，并禁止后续尝试。
- 真实业务秘密和现场原始证据留在受限工作区，不随公开源码、诊断包或 Release 分发。
